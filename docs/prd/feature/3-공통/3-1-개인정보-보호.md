# PRD: 개인정보 보호

## 1. 배경

- 현재 문제: 녹음 글·기록에는 수급자의 건강정보(민감정보)와 이름·전화번호가 들어간다. DB가 해외(Turso 도쿄)에 있고 AI(Groq)도 해외라, 평문 저장이나 그대로 전송은 개인정보보호법 위반 위험이 있다.
- 왜 지금 필요한가: 10/2 계획에서 평문 저장(P0-5)과 해외 API 전송(LAW-6)이 지적됐고, 심사위원이 직접 써 보는 본선 전에 막아야 한다.
- 관련 문서/이슈: `docs/prd/03-legal.md`, SEC-1·2·5, LAW-3·6·11, DIF-8, `_consent.ts`의 국외 이전 표

## 2. 목표

- 사용자가 무엇을 할 수 있어야 하는가: 사용자는 따로 할 일이 없다. 저장·전송되는 민감 정보가 보호된다.
- 기대 효과: DB가 유출돼도 녹음 글·기록·댓글·서명·수급자 이름·전화번호를 읽을 수 없고, AI에는 이름·전화번호가 가지 않는다.

## 3. 대상 사용자

- 주요 사용자: 요양보호사, 보호자, 수급자(정보주체)
- 보조 사용자: 없음
- 관리자 또는 운영자 영향: 운영자는 `ENCRYPTION_KEY`(base64 32바이트)를 관리해야 한다. 키를 잃으면 암호화된 데이터를 읽을 수 없다.

## 4. 범위

이번 작업에 포함:

- [x] AES-256-GCM 암호화(`encryptText`/`decryptText`): 녹음 글(`transcript`), 기록(`careRecord`, 특이사항 `notes`), AI 근거(`aiRawJson`), 서명, 게시판 댓글
- [x] 수급자 이름·전화번호, 보호자 전화번호 암호화(`sealPII`), 예전 평문도 읽기(`openPII`) (SEC-5)
- [x] AI 정리 전에 이름·전화번호를 역할어로 바꾸기(`redactForAi`: [수급자]·[보호자]·[요양보호사]·[전화번호]), 결과에서 이름 되돌리기 (LAW-6, DIF-8: 앱 안에서 처리, AI 호출 0번)
- [x] 올린 음성 파일은 글로 바꾼 뒤 저장하지 않는다 (서버가 받아 Groq로 보내고 글만 돌려줌)
- [x] 모든 서버 액션에서 로그인 확인과 내 수급자·방문만 접근 (`requireCaregiver`, `ownClientOrThrow`, `ownVisitOrThrow`) (SEC-1·2)

이번 작업에 포함하지 않음:

- [ ] 보호자 이름·장기요양인정번호·병력·알레르기·복용 약 암호화 (SEC-5 남은 일)
- [ ] 보호자 링크 만료·미리보기 봇 제외 (STB-5)
- [ ] 감사 로그 (OPS-4, P2)
- [ ] 키 교체(rotation)

## 5. 사용자 흐름

1. 요양보호사가 녹음·기록·서명하거나 보호자가 댓글을 쓴다.
2. 시스템은 저장 직전에 암호화하고, 화면에 보여 줄 때만 서버에서 푼다.
3. AI 정리 때는 이름·전화번호를 지운 글만 Groq로 보낸다.

## 6. 기능 요구사항

- FR-1: `encryptText`는 매번 새 12바이트 IV를 만들고 `IV + 인증태그 + 암호문`을 base64로 저장한다.
- FR-2: `ENCRYPTION_KEY`가 없거나 32바이트가 아니면 오류로 멈춘다.
- FR-3: `openPII`는 복호화에 실패하면 평문으로 보고 그대로 돌려준다 (옛 데이터 호환).
- FR-4: 댓글을 풀지 못하면 "(읽을 수 없는 댓글)"로 보여 준다.
- FR-5: `redactForAi`는 수급자·보호자·요양보호사 이름(성 뺀 이름 포함)과 전화번호(하이픈·공백 변형 포함)를 바꾼다.
- FR-6: 다른 요양보호사의 수급자·방문에 접근하면 "찾을 수 없어요" 오류를 낸다.

## 7. 비기능 요구사항

- 성능: 암복호화는 서버에서 필드 단위, 체감 지연 없음.
- 접근성: 해당 없음
- 보안: 키는 환경변수로만, 코드·저장소에 넣지 않는다. 브라우저로는 복호화한 화면만 보낸다.
- 로깅/모니터링: AI 실패 시 `console.error`에 오류만 남기고 녹음 원문은 남기지 않는다.

## 8. 수용 기준

- [ ] Given 요양보호사가 수급자 "홍길순"을 등록했을 때, When DB의 `client.name`을 보면, Then "홍길순"이 아닌 base64 암호문이다.
- [ ] Given 녹음에 "홍길순 어르신 혈압 135/85"가 있을 때, When AI로 보내는 글을 만들면, Then "[수급자] 어르신 혈압 135/85"가 된다.
- [ ] Given 요양보호사 A가 로그인했을 때, When 요양보호사 B의 방문 ID로 기록 확인 주소를 열면, Then 기록이 보이지 않는다.
- [ ] Given 음성 파일을 올려 글로 바꾼 뒤, When 서버 저장소와 DB를 보면, Then 음성 파일이 남아 있지 않다.

## 9. 검증 계획

- 단위 테스트: `npx tsx app/v1120/_redact.check.ts` (이름·전화번호 지우기, AI 결과 거르기), `npx tsx app/v1120/_signatures.check.ts`
- 통합 테스트: 없음. STB-7 권한 테스트(11/13 예정)
- 수동 확인: DB 브라우저로 암호화 칸 확인, 다른 계정으로 주소 직접 열기

## 10. 리스크와 열린 질문

- 리스크: 올린 음성 파일은 이름이 지워지지 않은 채 Groq(미국)로 간다. 동의 문구에 "올린 녹음 파일"을 보낸다고 적혀 있어 고지는 되어 있다.
- 리스크: 크롬 음성 인식은 소리를 Google로 보낼 수 있다 (동의 화면에 따로 안내).
- 열린 질문:
  - 보호자 이름·장기요양인정번호·병력 암호화를 11/20 전에 할지 (SEC-5)
  - 별명·주소 등 `redactForAi`가 모르는 개인정보가 녹음에 나오면 어떻게 할지
  - 키를 잃거나 바꿀 때 기존 데이터를 다시 암호화하는 절차
